# kaobots

AOSharp profession handlers and managers, based on [AOSp Bots](https://gitlab.com/aosharp-plus/aosp-bots).

Credit to **Knowidea / never-knows-best (Know)** and all original contributors. This repository builds on their work; original source notices are retained. Imported from upstream source commit `59de6fe9a0ec297e71fbf4338fdcb01683947865`.

## Additions in this source import

- **Master’s Bidding:** separate attack/support pet toggles in the shared Pets buff window, requirement checks, specific offensive-proc conflict checks, and `/petstats` diagnostics. The nano must be uploaded on the character for the option to appear.
- **Agent snare-perk controls:** Tranquilizer appears in Holds; disabled Tranquilizer and Soften Up actions are removed from the pending queue. Already submitted actions cannot be recalled.
- **Pet Commands for every profession:** control pet owners on the same IPC channel from a leader such as Keeper.
- **HelpManager 42 Autofence:** optional per-character attempts to use a nearby Biological Transceiver until its protection buff is present. Requires 10 free NCU; delays attempts while busy and stops attempting when the object is absent or out of range. It does not navigate or manage pet movement.
- **Manager Sync:** stop repeated syncbag scans after a scheduled pass; preserve reopening after zoning. Give OnUpdate work a nonblocking one-second startup grace period. Remember the saved outside team invite preference across loads; save invite state changes immediately.

## Manager startup on the new client

Manager Sync, HelpManager and Attack Manager now attempt their normal startup on either client instead of returning immediately on the new engine. Existing settings, enable switches and error handling remain in place. This removes the blanket startup refusal so actual compatibility failures can be investigated; it does not establish that every manager feature works on the new client. Source review only; no builds, tests, releases or automatic CI were run.

## Radar

Radar **1.0.27** is a local vicinity HUD for one character, with no IPC. Build `Utility.Radar` in the solution and add `ADDME-Utility.Radar.dll` to AOSharp. Keep the matching output dependencies and updated `UI/RadarProfessions.xml`, `UI/RadarPlayers.xml`, `UI/RadarEditor.xml` and `UI/RadarTarget.xml` beside the plugin. It uses AOSharpSDK 1.0.106 and targets .NET Framework 4.8/x86.

The transparent menu is ordered **All players**, **Towers**, **NPCs**, **Pets**, then **Raid** and **Team** when available, followed by all fourteen professions and **Others**. Every visible category has a count, including zero. **All players** and profession filters contain only other players. **Towers** contains non-player, non-pet characters with the engine's positive `CharacterFlags.Tower` flag; names, HP and guessed `TowerType` values are not used. **NPCs** contains the remaining non-player characters, including humanoid vendors. **Pets** contains characters positively identified by `IsPet`, without requiring a loaded owner; pet classification takes precedence over towers. **Others** contains loaded non-character entities such as terminals, vending machines, doors, chests and corpses. Weak creatures or unresolved HP do not move into Others.

A fresh injection starts with no category selected: the radar shows every loaded entity within range, including players, towers, NPCs, pets and objects. This unfiltered overview uses the live dynel list each frame. Click a category to filter the radar and browse its entity list; click the active category again to return to the overview and hide the list. **All players** remains an explicit players-only filter. Category browsing never changes AO's target, and AO target changes never change your chosen filter or leave the overview. The entity list is independently positioned on the right and stays hidden with no category selection; its empty editing outline can still be revealed and adjusted. Player names retain **(level/AI level)**, sorted by highest level, then highest AI level, with alphabetical ties. Unknown player levels show **?**. Towers, NPCs, pets and objects show available level and **HP current / maximum**; object level is labelled **Lv/QL** because it can represent template quality. Missing or inconsistent pools are omitted. Towers, NPCs and pets can have levels above 220.

**Team** appears only while the client reports a team; **Raid** appears only in a raid. A raid shows both choices: Team is your own six-person subteam, Raid is the whole raid. Raid entries are grouped with your team first, then other subteams by their native team index; the existing descending level and AI level, then alphabetical name ties remain within each group. Team and other category lists retain that existing level/AI-level/name sort. Team/Raid counts and entity lists include loaded other players only, excluding yourself. Roster membership can be known beyond loaded vicinity, but it supplies no world position, so Radar does not invent distant markers. Leaving a selected group category returns to the full overview without changing AO's target. Changes to Team/Raid availability rebuild category content and can reset its native scroll; saved geometry is retained.

The native team/raid roster supplies profession and level without a profession request. Valid roster data feeds the loaded-player snapshot and profession resolver first, with ordinary cached-stat/request fallback for unknown values and other players. The target inspector also uses these two roster values when available and labels them **roster**; its raw-stat section keeps the actual client-stat readings for comparison. AI level, HP, nano and positions retain their existing sources. Roster collection runs at the existing 250-ms snapshot cadence, including while hidden. If the optional roster API fails, that path is reported and disabled for the current injection while the other categories continue.

The centre radar keeps your blue arrow pointing up and rotates the field with your character's facing. Five white rings mark **20, 40, 60, 80 and 100 horizontal metres**, with rotating compass positions. In the unfiltered overview and Team/Raid views, your team is green, other raid members yellow, pets pink and unrelated entities white. Your own team takes precedence over raid membership. You remain blue and the selected entity remains red. Other explicit category filters keep their yellow markers. Characters use heading arrows; objects and characters without a usable horizontal heading use diamonds. Membership and pet colours update with the roster snapshot; marker poses still update each drawing frame. By default the complete radar occupies about half the screen height, with a 500-pixel outer circle at 1080p; its position and size can be edited. Only entities already loaded by your client are available; static scenery is not necessarily a dynel, and 100 metres is a display scale rather than a guaranteed discovery distance.

Activity appears as short bursts of three tiny amber dots travelling from a source marker toward its recipient. In the default unfiltered overview, every received attributable interaction between valid loaded dynels can appear, regardless of profession or player/NPC/pet/object category. An explicit category limits bursts to activity involving that category, your current selected entity or yourself; a direct participant outside the filter briefly gets a faint context marker. This does not change counts, lists or AO's target. Both endpoints must be loaded, valid and within the radar's 100-metre horizontal radius. Positions/headings are projected each frame, so bursts follow turning, movement and resizing. Missing headings and non-character objects use their diamond centres. Self-targeted activity and overlapping endpoints make a tiny loop from the marker back to itself. The thin strokes stay beneath normal markers and clip to the outer ring.

Supported received messages include regular hits, specials, misses, reflect and shield damage, and all health-damage notifications including healing; attack-start and queued-special notifications; nano cast activity; effect add/refresh, attributed health/nano transfers, drain and detection feedback. Damage and healing stream distinctions follow [Mali's damage meter](https://gitlab.com/Pixelmania/malis-damage-meter/-/blob/a73809fc051e0485e163218bdf996566a66a3ea4/N3MessageCallbacks.cs); additional field roles are checked against the [native action notes](https://github.com/reiserFSs/aorust/blob/3e66d7384c0a0c74e47f89a14a1a5a4053d9bfb9/docs/zone/actions.md). Casts and queued actions show activity rather than guaranteeing a landed effect. Effect add/refresh notifications can also restore existing effects during login. Perk effects appear through their attributable result messages; queue/training/recharge fields are not treated as world actors. Absorb-only, buff-removal and raw stat updates without a verified source cannot form a directed burst. Unknown origins are never replaced with the current target or a guessed attacker.

This is a schematic activity display: each supported received event launches one three-dot burst. A single action may generate several notifications and therefore several bursts. Processing cadence drives the display; the SDK supplies no original server timestamp. There is no guessed continuous firing, damage-based dot sizing or general sequence ID for authoritative deduplication. Observer traffic may be incomplete, delayed or batched, and server broadcast/client load range limits what can appear.

Each dot travels for 420 ms, with 55 ms between launches. Events expire after 600 ms; the buffer holds at most 128 events (at most 384 dots), dropping oldest entries if full. Intake remains active in both the unfiltered overview and the hidden HUD. Expiration continues while hidden, so showing the radar displays only recent activity. Zoning, changing character and unloading clear activity. Switching filters can reveal a recent event's remaining tail. Intake copies only identities and timing, adds no information requests or actions, and creates no native GUI objects. The flying-pixel event handling, timing, paths and drawing are unchanged in this update. Copy the updated `UI/RadarProfessions.xml` with the new DLL; existing saved geometry remains compatible and no reset is needed.

Click a name to set AO's ordinary selected target and mark that same entity with a red circle and direction line. A fixed-width red > beside its row shows selection; names stay white so target-only changes do not recreate the list. Clicking an already selected name keeps it selected. Selecting a loaded entity through AO updates its red radar/world marker, resource readouts and target inspector while preserving the current category or unfiltered overview. Its list row is marked if it belongs to the category you are browsing. Selecting a target during your own fight therefore keeps the wider overview intact. Clearing AO's target, selecting yourself or targeting an unavailable entity removes the Radar entity highlight. Player readouts remain **above the circle**: red **current HP / maximum HP**, with blue **current nano / maximum nano** beneath it. Towers, NPCs, pets and objects show a red HP row there only when a usable pool is available. The centred line-drawn digits face the camera, scale naturally with distance and have no background. The marker follows the entity's location; it does not recolour its body model. Synchronization uses AO's ordinary selected target, separately from its fighting target. Radar does not issue an attack command.

Resource and level values come from the client cache and may be incomplete or stale. Invalid player pool values show **?**; the remote maximum-nano placeholder 10 is also treated as unknown. Non-character pools with maximum HP of 1 or less are omitted. Profession information is requested gradually for players without selecting them or opening Info windows; no information requests are added for towers, NPCs, pets or objects. Native debug drawings follow the client's visibility behaviour. The renderer assumes the normal full-display game viewport.

- `/radar` toggles HUD visibility.
- `/radar on` shows it.
- `/radar off` hides it while background collection continues.

Hiding is a visibility change: roster snapshots, gradual profession resolution, AO target tracking, target-inspector data/stat sweeps and activity intake continue at their existing rates. Resolver attempts/deadlines, the current filter and target, and collected values are retained. Showing uses the latest snapshot without starting a fresh discovery pass. Unload the plugin to stop its background processing.

Hidden Radar skips native window creation, text updates, hover/cursor handling and all radar/world drawings. Existing text windows are hidden rather than closed, preserving their bindings and scrolling when the roster is unchanged. Structural roster/name/level changes collected while hidden are applied on show and still recreate the entity list, with its existing scroll-reset limitation. Deferred UI clicks are cancelled when hiding. The target inspector separates collection from view updates, so its native fields refresh from retained values on show.

- `/radar reset` restores and saves all four defaults: radar centred, categories left, entity list right, target inspector above the radar.

The category menu has its own viewport on the left; the entity list has its own viewport on the right. Neither follows the selected category row. The fourth viewport is a wide, shallow target inspector above the radar (760 by 112 screen units at 1920 by 1080); it can be moved or resized independently. Hover near any panel's outline for its labelled **Move** and **Resize** grips, using the same progressive cyan reveal and amber drag feedback as the radar. Each panel saves position and size independently per character. The nearest idle frame receives hover controls; an active drag retains ownership when crossing another frame.

Text-panel resizing changes only the visible viewport. **SMALL** text and row heights stay fixed. Labels, counts and HP fields use their native font width and height, aligned at the top of fixed-height rows; a trailing blank spacer absorbs spare row width. Text widgets request native clipping to their own bounds. Native vertical and horizontal scrollbars appear when the full content does not fit, including category lists on short viewports and large entity rosters. The entity list has no artificial row limit. Hover inside a text panel and use the mouse wheel, or drag its native scrollbar. Side-panel grips sit above/below the scroll body so they do not cover rows or scrollbar controls. The radar keeps square resizing; the text panels resize width and height independently.

Move the mouse near a panel's rectangular perimeter to reveal its cyan editing outline progressively. The reveal band reaches 20 screen units from the perimeter or grips, with a 32-unit pre-arm band and 40-unit leave threshold. Corners and rails grow as you approach, rather than switching abruptly between hidden and visible. The middle stays uncovered. Two small native captions identify each panel's controls: drag **Radar - Move**, **Categories - Move**, **Entities - Move** or **Target - Move** above the corresponding body, or its **Resize** grip near the lower right. Text-panel resize grips sit in a footer below the scroll body. Only these labelled grips perform manipulation. The outline stays fully revealed with amber feedback during a drag, including when the pointer leaves its original area. The radar remains circular and its outer ring remains 100 metres.

Releasing a grip saves a changed layout automatically. Moving away lets the frame and captions disappear; leaving the frame also commits any unattempted dirty preview. There is no normal edit/save command sequence or Save button. Position and size are stored per character under `%LOCALAPPDATA%/AOSharp/Radar/<character ID>/`: `layout.xml` retains the radar schema, with separate `categories.xml`, `entities.xml` and `target.xml` for the text panels. Existing radar geometry is retained until reset; new text panels use defaults until adjusted. Hovering without adjusting anything does not write settings. Saving uses a temporary file and atomic replacement. A failure is reported in chat and retains the preview with red frame feedback, without retrying the disk write every frame.

Optional commands apply to all four layouts: `/radar edit` shows the HUD and briefly reveals the grips; `/radar lock` retries unsaved previews; `/radar cancel` restores the last saved geometry. Automatic saves mean Cancel does not undo an already saved drag. Layout commands issued while hidden are applied when the HUD is shown. Reset still works when the hover editor is unavailable.

The outlines use the existing overlay renderer. Each editor uses only two small native grips. The three text bodies use transparent native scroll views; there is no editing window across the radar's centre. Native drag handling owns grip input; read-only foreground/client-coordinate mouse polling supplies proximity and release detection. Focus or display changes suspend tracking until a confirmed mouse-up. Hiding saves the last validated dirty preview if possible and removes the grips; a failed save retains its preview and error state for the next show/retry. Zoning, changing character or unloading clears world caches and ends the current editor session. Missing UI/native exports or unusable geometry disable the hover editor while retaining the radar and side HUD. This revision still needs an in-game check of independent positioning, native scrollbar/wheel behavior and panel sizing with the running client/skin.

The target inspector follows AO's ordinary selected target directly, including yourself and objects outside the filtered roster. It stays present with a selection prompt when there is no valid target. Its fixed header identifies the target while its body scrolls vertically and horizontally. The initial summary has three columns; resizing changes the viewport rather than font size. The panel keeps its native window and scroll position across value and target changes.

Available fields include name, runtime identity type and instance (decimal/hex), three-dimensional and horizontal global distance, height difference, relative bearing, positions, rotation, heading, movement and radius; HP/nano current, maximum and percentage; level/QL, AI level, profession, breed, side, title, organization/team/race stats; character validity-related flags, team/line-of-sight state, fighting target and pet owner when loaded; object item flags and lock/open bits for recognized item types. Runtime instances are not database AOIDs. A separate section lists cached template/AOID candidate stats without assuming that every target has an item template.

Below the summary are cached effects (name, nano ID, NCU, nanoline, stacking order and timers), cached equipment/inventory where available (actual slot, item name, low/high AOIDs, QL, charges and unique identity), then all 705 distinct named `Stat` entries exposed by this SDK, in numeric order. The effect owner is the affected target, not the caster. Empty caches do not prove an empty inventory or the absence of effects, and effect timers may be coarse. Missing data shows **?**; inapplicable typed fields show **n/a**. Raw stats use stored-value mode 0 and preserve zero and negative values: zero can mean unset, and availability/freshness cannot be established for every field. These are exploratory client-cache readings, not a complete server-side character sheet.

Inspector summary values refresh every 250 ms, effects and inventory every second. Raw stats are read in batches of at most 32 per update, at least 16 ms apart, with a two-second pause after a complete sweep. Changing targets clears previous values immediately and starts a new sweep. Only changed text is sent to the native widgets; the inspector does not rebuild itself during polling. It issues no target-selection, attack, explicit information request or inventory-use action. Existing gradual player profession resolution remains separate. Inspector display failures disable that panel for the current injection and leave its data collector running; a target-data failure disables that collector and panel for the current injection while the other collectors continue. Both are reported in chat.

Roster snapshots refresh every 250 ms; visible counts and lists use those snapshots. Normal-target changes are tracked each game frame. While visible, marker positions, headings and selected-entity world readouts are sampled each drawing frame. Target changes request an immediate list refresh. Radar clears its local selection when the target becomes unavailable or you zone; these actions never clear or change AO's target. Target tracking continues while hidden, and showing uses the current observed target. The browse category persists for the current injection until you click another category, toggle the active one back to the overview, or leave its selected Team/Raid group. The list is populated before native window creation and replaced when its category, roster or displayed names/levels change. Those structural replacements reset native scroll position because the SDK exposes no scroll-offset accessor. Target-only selection changes within an unchanged list update the red row marker in place, and HP updates existing text fields, retaining the native scroll view in both cases. Geometry stays fixed through these refreshes. The old `UI/Radar.xml` counter template is retained but unused.

The native drawing approach was informed by [Mali's Dungeon Map](https://github.com/MalishadeAO/malis-dungeon-map-2.0), the [aorust native GUI and rendering notes](https://github.com/reiserFSs/aorust), and [ao-vk's native renderer reconstruction](https://github.com/wannabuh/ao-vk). ## Native raid bar setup

**Utility-RaidBars 1.0.0 is an experimental native-layout utility.** It prepares the client's own detached raid bars as six adjacent team columns, with six member slots per column. It does not draw replacement health/nano bars or create raid members. Live movement and persistence still require an in-game trial; a successful settings read-back alone does not establish that existing bars moved.

Build `Utility.RaidBars` and register `ADDME-Utility.RaidBars.dll` in AOSharp, keeping matching dependencies and `UI/RaidBars.xml` plus `UI/RaidBarsGrip.xml` beside the DLL. The project targets .NET Framework 4.8/x86 and AOSharpSDK 1.0.106. Loading opens `/raidbars` setup and reads settings without changing them.

- **Align 36 slots** orders teams left to right and member slots top to bottom. Left/Top set the first column's origin; Team gap/Row gap set spacing. Negative gaps overlap bar edges. Existing bar frame dimensions are retained; default dimensions are 168 by 31 when no saved frame exists. Empty roster slots are prepared for later members.
- **Move all** opens one small native title to drag the arrangement. **Move teams** opens six titles, one per column. These are setup handles; grouping requires the utility to be loaded. Native individual-bar dragging is locked during setup. Changing display size or zoning ends handle editing; reopen it afterward.
- **Lock bars / Unlock bars** use AO's global raid-bar lock. **Done** closes setup and leaves that lock on. Closing setup or unloading removes only the utility's windows and retains the last accepted settings. AO owns normal preference saving; verify the result after unloading and a normal relog.
- **Read current** reloads the client's settings. **Details in chat** reports native slot counts, lock and the snapshot path. **Undo setup** restores the pre-edit positions/enabled states and lock. Frame records introduced for previously absent slots remain dormant with their enabled flags false. The first successful edit after loading creates that session's undo copy; it is not an unlimited history.

Commands: `/raidbars`, `/raidbars align`, `/raidbars edit all`, `/raidbars edit teams`, `/raidbars lock`, `/raidbars unlock`, `/raidbars done`, `/raidbars read`, `/raidbars undo`, `/raidbars status`.

The utility uses the native character-preference loader and exports snapshots for read-back. It imports only `RaidBarConfig` and `LockRaidBars`, preserving other settings, and attempts restoration after a failed apply. It never overwrites a live `Prefs.xml` directly. Snapshots and the two-setting `undo.xml` live in the utility's per-character AOSharp data folder. There is no forced archive reset or guessed raid-window name/offset. No dependency on Radar or Manager.Raid is added.

For the first trial, use AO's normal raid controls with two characters. Put them in the same team to check vertical order and spacing, then separate teams to check horizontal spacing and group movement. Check that the actual health bars follow the setup titles. Finish, unload, and verify the native positions/lock remain, including after a normal relog. If only the handles move or the client restores old positions, use Undo and report which client/skin was used; that means the live native window path needs further investigation. Neither client engine has been runtime-validated for this utility yet.


## Tower Info

**Utility-TowerInfo 1.0.1** is an on-demand tower inspection utility. Build the solution's `Utility.TowerInfo` project and add `ADDME-Utility.TowerInfo.dll` to AOSharp with the normal matching dependencies. No XML files or handler/Radar plugin are required.

- `/tower info` (or `/tower`): inspect the selected known tower, otherwise the nearest tower known to this client. Prints playfield/coordinates, distance, faction and received tower class, then requests server details without changing your target. Replies add QL, owner organization ID, health and tower item IDs. Control-tower replies also expose the server's raw timer and next-gas fields; their encoding/units are not yet verified, so no countdown is derived.
- `/tower list`: list up to 20 nearest known towers in this playfield. Zoning with the utility loaded supplies the server's tower snapshot; injecting after arrival initially gives only loaded towers/updates.

A nearest tower is **not proof of which site you are standing in**. This version does not resolve site names/numbers/boundaries/level ranges or organization names, and cannot establish an empty site's peace/war state or planting time. No visible/known tower does not prove that a site is empty or plantable. Use the native Controller Build Check for its live placement requirements. Tower QL is not the site's level range.

Cached replies are labelled with their age; each info command requests fresh details (two-second throttle, eight-second reply timeout). This is a one-shot read-only utility: it never plants, attacks, changes target or automatically refreshes requests. Packet updates are cached only for the current playfield; no raw tower-proxy memory offsets are used. Source delivery only; compilation and in-game verification are pending.

## Sync area benchmark

Manager Sync 2.0.14 counts its OnUpdate callbacks on every loaded client, including while Sync is disabled. It separates foreground/background cycles and elapsed wall time, reports rates and the longest callback gap, and starts a new sample after zoning or playfield initialization. One compact chat summary appears after the transition; unloading saves the final sample to the file.

Per-character records are in `%LOCALAPPDATA%\AOSharp\ManagerSync\<character>\sync-benchmark.log`. UTC AREA_START/AREA_END and ZONE_START/ZONE_END records let you compare clients' observed arrival/departure times and zone durations. Failed or interrupted zoning is labelled. These timestamps describe callbacks observed by the plugin; a stalled game can delay the callbacks themselves. Rates measure Sync callbacks, not rendered FPS. Focus time between callbacks is attributed to the preceding observed focus state, so long stalls make the split approximate.

Keep the same two clients and settings, zone through quiet areas, swap the foreground driver, then repeat in a populated city. Compare the files by character, area ID and UTC time. No per-frame file/chat writes, extra IPC traffic or movement changes are added.
